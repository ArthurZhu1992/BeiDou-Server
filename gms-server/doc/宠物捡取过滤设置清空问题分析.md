# 宠物捡取过滤设置清空问题分析

## 结论

这个问题不是单点 bug，而是以下 3 段逻辑组合后导致的：

1. **登录加载时只为“当前已召唤”的宠物加载过滤配置**
2. **后续召唤宠物时没有重新从数据库补载过滤配置**
3. **角色保存时会先删库再按当前内存配置重写**

因此会出现两种现象：

- **表象清空**：客户端看到过滤列表变空，但数据库里原始配置可能还在
- **真实清空**：后续触发空列表回写或角色保存后，数据库中的 `petignores` 记录也被删掉

---

## 关键结论与确切位置

### 1. 导致“过滤配置没有被加载”的根因位置

文件：

- `src/main/java/org/gms/client/Character.java`

关键位置：

- `Character.loadCharFromDB(...)` 中只在宠物 `pet != null && pet.isSummoned()` 时才加载过滤配置
- 相关代码位置：
  - `src/main/java/org/gms/client/Character.java:6285`
  - `src/main/java/org/gms/client/Character.java:6287`
  - `src/main/java/org/gms/client/Character.java:6289`
  - `src/main/java/org/gms/client/Character.java:6290`

逻辑说明：

- 登录角色时，背包里的宠物物品会被遍历
- 如果该宠物是“已召唤”状态，才会执行：
  - `chr.resetExcluded(item.getPetId())`
  - 从 `petignores` 表加载记录后逐条 `chr.addExcluded(...)`
- 如果宠物在登录时**未召唤**，那么它的过滤配置**不会进入角色内存**

这就是问题的第一个根因。

---

### 2. 导致“召唤后过滤列表仍然为空”的直接位置

文件：

- `src/main/java/org/gms/client/processor/action/SpawnPetProcessor.java`

关键位置：

- `src/main/java/org/gms/client/processor/action/SpawnPetProcessor.java:88`
- `src/main/java/org/gms/client/processor/action/SpawnPetProcessor.java:93`

逻辑说明：

- 宠物被召唤时，代码只做了：
  - `chr.addPet(pet)`
  - `chr.commitExcludedItems()`
- 这里**没有**按 `petId` 重新从数据库 `petignores` 表补载配置

而 `commitExcludedItems()` 的行为只是：

- 把当前角色内存中的 `excluded` 配置发送给客户端

如果该宠物的过滤配置在登录阶段没有被加载到内存，那么这里同步出去的就是空配置。

也就是说：

- **未召唤状态登录**
- **当前会话内再召唤该宠物**

会直接导致客户端看到“过滤设置被清空”

---

### 3. 导致“数据库里的过滤设置最终也被清空”的位置

#### 3.1 客户端空列表回传时的重置点

文件：

- `src/main/java/org/gms/net/server/channel/handlers/PetExcludeItemsHandler.java`

关键位置：

- `src/main/java/org/gms/net/server/channel/handlers/PetExcludeItemsHandler.java:53`
- `src/main/java/org/gms/net/server/channel/handlers/PetExcludeItemsHandler.java:58`
- `src/main/java/org/gms/net/server/channel/handlers/PetExcludeItemsHandler.java:64`

逻辑说明：

- 服务端收到宠物排除物品包后，先执行：
  - `chr.resetExcluded(petId);`
- 然后再按客户端传回的列表逐条 `addExcluded`

如果客户端此时提交的是空列表，那么内存里的该宠物过滤配置会被清成空集合。

#### 3.2 保存角色时的删库重写点

文件：

- `src/main/java/org/gms/client/Character.java`

关键位置：

- `src/main/java/org/gms/client/Character.java:7511`
- `src/main/java/org/gms/client/Character.java:7512`
- `src/main/java/org/gms/client/Character.java:7517`

逻辑说明：

- 角色保存时，会遍历 `getExcluded()`
- 对每个宠物先执行：
  - `DELETE FROM petignores WHERE petid=?`
- 然后再把当前内存中的过滤项批量插回

如果这只宠物当前内存里的过滤集合为空，那么保存后的结果就是：

- 旧记录被删除
- 新记录不插入
- 数据库里的过滤配置被真正清空

## 完整问题链路

### 场景一：登录时宠物未召唤，之后再召唤

1. 角色登录
2. 该宠物在数据库里有过滤配置，但登录时不是召唤状态
3. `Character.loadCharFromDB(...)` 不会加载这只宠物的 `petignores`
4. 当前角色内存里没有这只宠物的过滤配置
5. 玩家在当前会话内召唤该宠物
6. `SpawnPetProcessor` 没有补载数据库配置，只执行 `commitExcludedItems()`
7. 客户端收到的是空列表
8. 玩家看到“过滤设置被清空”

这是**表象清空**。

### 场景二：表象清空后又被真正落库

在场景一基础上继续：

1. 客户端把当前空列表提交给服务端
2. `PetExcludeItemsHandler` 先 `resetExcluded(petId)`
3. 因为列表为空，没有新的 `addExcluded`
4. 角色保存时，`Character.saveToDB()` 先删掉 `petignores` 旧记录
5. 再按空集合回写，最终数据库里也变空

这是**真实清空**。

---

## 为什么说是“某些情况下”才发生

因为它不是所有宠物、所有时刻都会触发，而是依赖下面这个条件：

- **宠物在角色登录时不是召唤状态**

如果宠物在登录时已经处于召唤状态，那么 `Character.loadCharFromDB(...)` 会把它的过滤配置加载进内存，这时后续 `commitExcludedItems()` 就能正常同步给客户端，不会表现为空。

所以这个问题的核心触发条件非常明确：

- **登录时未召唤**
- **登录后在当前会话内再召唤**

## 最终判断

### 确切根因

**宠物过滤配置的数据库加载逻辑被错误地限定在“登录时已召唤宠物”上，而召唤流程本身又没有补载数据库配置。**

### 确切导致问题的位置

主根因位置：

- `src/main/java/org/gms/client/Character.java:6287`

直接表现位置：

- `src/main/java/org/gms/client/processor/action/SpawnPetProcessor.java:93`

最终把数据库清空的位置：

- `src/main/java/org/gms/client/Character.java:7512`
